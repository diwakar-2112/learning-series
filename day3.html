1. Core Types, any vs unknown vs never & Structural Typing

Beginner Mental Model

TypeScript is JavaScript with a compile-time type checker. When you build an Angular, Next.js, or Node app, tsc checks all types before the code runs and then erases every type annotation when compiling down to plain JavaScript! That means TypeScript adds zero runtime overhead — and also means TypeScript types alone do NOT validate incoming API/JSON data at runtime (that's why you use Zod in your Express backend!).

Real-Life Analogy: Airport Security vs Boarding TypeScript is like an architect inspecting building blueprints (compile-time) before construction begins — it catches mismatched pipes and missing beams early. Runtime validation (like Zod) is like the security guard checking IDs at the actual building door when strangers (external HTTP requests) walk in.

any vs unknown vs void vs never (Must-Know Comparison!)

Type Meaning Can Assign Anything To It? Can You Call Methods On It Directly?
any Turns OFF type checking (escape hatch — avoid!) Yes Yes (dangerous! Crashes at runtime if wrong)
unknown Type-safe top type ("I don't know what this is yet") Yes NO! Must narrow/validate first with typeof / type guard!
void Function returns no useful value (undefined) N/A (return type) N/A
never Bottom type — value that can never exist (function throws or loops forever; empty union) Nothing can be assigned to never! Used for exhaustive switch checks!

Structural Typing ("Duck Typing") — Experienced Level

Unlike Java or C# (Nominal typing, where two classes with identical fields aren't compatible unless explicitly related), TypeScript uses Structural Typing: compatibility is based on shape! 

type Point2D = { x: number; y: number };
type Point3D = { x: number; y: number; z: number };

function logPoint(p: Point2D) {
  console.log(p.x, p.y);
}

const p3: Point3D = { x: 1, y: 2, z: 3 };
logPoint(p3); // ✅ VALID! Point3D has at least { x, y }!

// Exception: Excess Property Check on inline object literals!
// logPoint({ x: 1, y: 2, z: 3 }); // ❌ Compile Error when passing fresh object literal directly!

Interview Questions & Practice Problems

Q1 (Interview): When should you prefer interface vs type?
Show Answer

Use type for unions, intersections, tuples, function signatures, and mapped/utility transformations. Use interface for object contracts, public library APIs, class implements, or when you need declaration merging (like augmenting Express Request). Most importantly: stay consistent within a codebase!

3. Unions, Intersections & Discriminated Unions

Unions (|) vs Intersections (&)

  • Union (A | B): Value can be either A or B. You can only access properties guaranteed on BOTH until you narrow!
  • Intersection (A & B): Value must satisfy ALL properties of A AND B combined. (If A has id: string and B has id: number, id becomes never!).

Discriminated (Tagged) Unions — The Cleanest Pattern in TypeScript!

Instead of writing sloppy optional flags like { loading: boolean; data?: T; error?: string } (which allows impossible states like loading: true AND error: "Failed" at the same time!), model states using a shared literal tag (e.g. status or kind): 

type AsyncState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; message: string };

function renderTickets(state: AsyncState<string[]>): string {
  switch (state.status) {
    case "idle":
      return "Click load to fetch tickets";
    case "loading":
      return "Spinner...";
    case "success":
      return `Loaded ${state.data.length} tickets`; // TS knows 'data' exists ONLY here!
    case "error":
      return `Error: ${state.message}`;             // TS knows 'message' exists ONLY here!
    default: {
      // Exhaustiveness check! If someone adds { status: "retrying" } above and forgets a case,
      // TypeScript flags a COMPILE ERROR right on this line!
      const _exhaustive: never = state;
      return _exhaustive;
    }
  }
}

}

4. Generics (<T>) & Built-in Utility Types

Beginner Mental Model

Regular functions accept value parameters like (x: number). Generics let functions, interfaces, and classes accept type parameters like <T> — preserving the exact input type all the way to the return type without losing safety to any!

Real-Life Analogy: Standardized Shipping Box A generic ApiResponse<T> wrapper is like a clear glass shipping box. Whether you put a Ticket inside (ApiResponse<Ticket>) or a User[] inside (ApiResponse<User[]>), the box label (success, timestamp, data) stays identical while TypeScript remembers the exact item inside! 
// 1. Generic Interface
interface ApiResponse<T = unknown> {
  success: boolean;
  data: T;
  requestId: string;
}

// 2. Generic Function
function wrapResponse<T>(data: T): ApiResponse<T> {
  return { success: true, data, requestId: "req_123" };
}
const res = wrapResponse({ id: 1, title: "Bug" }); // res.data is inferred as { id: number; title: string }!

// 3. Generic Constraints (extends) + keyof!
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const ticket = { id: 101, priority: "P1" };
const p = getProperty(ticket, "priority"); // Type is string!
// getProperty(ticket, "nonExistent");     // ❌ Compile Error! "nonExistent" not in keyof ticket!

Essential Built-in Utility Types (Used Daily in Angular/Next.js/Prisma!)

Utility Type What It Does Real-World Example
Partial<T> Makes all properties of T optional PATCH /tickets/:id update payload: Partial<Ticket>
Required<T> Makes all optional properties required Final validated config object
Readonly<T> Marks all top-level properties readonly NgRx / Signal immutable state
Pick<T, K> Selects a subset of keys K from T Pick<Ticket, "id" | "title"> for list view
Omit<T, K> Removes keys K from T Omit<User, "passwordHash"> for safe public DTO!
Record<K, V> Dictionary mapping keys K to values V Record<TicketStatus, number> for status counts
ReturnType<F> / Awaited<P> Extracts return type of function / unwrapped Promise value Inferring Prisma query result types cleanly!

Q1 (Interview): What is the difference between Pick<T, K> vs Extract<U, V>, and Omit<T, K> vs Exclude<U, V>?
Show Answer

Pick and Omit operate on Object property keys. Extract and Exclude operate on Union types (e.g., Exclude<"A" | "B" | "C", "C"> → "A" | "B").

5. Type Narrowing & Custom Type Guards

Beginner Mental Model

Type Narrowing is how TypeScript tracks your runtime if / switch / return checks (Control Flow Analysis) and shrinks a broad type (like string | number | null) down to a specific type inside that block!

All 6 Type Narrowing Techniques

// 1. typeof guard (Watch out: typeof null === "object" in JS!)
function formatId(id: string | number) {
  if (typeof id === "number") return `TKT-${id.toFixed(0)}`;
  return id.trim().toUpperCase();
}

// 2. Truthiness & Equality narrowing (handles null/undefined)
function printTitle(title?: string | null) {
  if (!title) return; // Narrows out undefined, null, and ""
  console.log(title.toUpperCase());
}

// 3. 'in' operator narrowing
type Admin = { permissions: string[] };
type Customer = { company: string };
function describeAccount(acc: Admin | Customer) {
  if ("permissions" in acc) {
    console.log("Admin perms:", acc.permissions.join(", "));
  } else {
    console.log("Customer org:", acc.company);
  }
}

// 4. 'instanceof' narrowing (Classes & Errors)
function handleError(err: unknown): string {
  if (err instanceof Error) return err.message;
  return "Unknown error";
}

// 5. Custom Type Predicate ('param is Type') — Huge Interview Favorite!
interface Ticket { id: number; title: string; }

function isTicket(value: unknown): value is Ticket {
  return (
    typeof value === "object" &&
    value !== null &&
    "id" in value && typeof (value as any).id === "number" &&
    "title" in value && typeof (value as any).title === "string"
  );
}

// 6. Assertion Function ('asserts cond' or 'asserts val is T')
function assertNonNull<T>(val: T, msg: string): asserts val is NonNullable<T> {
  if (val === null || val === undefined) throw new Error(msg);
}
Interview Trap: Type Assertion (as) vs Type Guard (is) Writing const t = data as Ticket; tells the compiler "Trust me, shut up" — zero runtime safety! A Type Guard (isTicket(data)) performs an actual runtime check, keeping your app safe from malformed API responses.

// support-ops.types.ts
export type TicketPriority = "P1" | "P2" | "P3";
export type TicketStatus = "OPEN" | "IN_PROGRESS" | "CLOSED";

export interface Ticket {
  readonly id: string;
  title: string;
  priority: TicketPriority;
  status: TicketStatus;
  assigneeId: string | null;
}

export type UpdateTicketInput = Partial<Omit<Ticket, "id">>;

export interface PaginatedResult<T> {
  items: T[];
  total: number;
  page: number;
}

// Generic filter helper constrained to keys of T
export function filterByField<T, K extends keyof T>(
  list: readonly T[],
  key: K,
  value: T[K]
): T[] {
  return list.filter(item => item[key] === value);
}

// Type-safe immutable patch function
export function patchTicket(ticket: Ticket, patch: UpdateTicketInput): Ticket {
  return { ...ticket, ...patch };
}

// Custom Type Guard
export function isCriticalOpenTicket(ticket: Ticket): boolean {
  return ticket.priority === "P1" && ticket.status !== "CLOSED";
}

8. Day 3 System Design: Databases, Indexing, ACID & Connection Pooling

Part A: SQL (PostgreSQL) vs NoSQL (MongoDB/DynamoDB)

  • Why your Support Operations Center uses PostgreSQL (SQL): Tickets, Users, Organizations, Comments, and Audit Logs are highly relational and require strict schemas, foreign-key integrity, complex joins/aggregations (e.g., SLA reports), and multi-row transactions.
  • When NoSQL shines: Massive horizontal write-heavy logs, flexible un-joined documents, or simple key-value lookups at millions of RPS. (Plus PostgreSQL's JSONB and pgvector cover most semi-structured & AI embedding needs without adding a second DB!).

Part B: How Database Indexes Actually Work (B-Tree)

Without an index on tickets(status), running WHERE status = 'OPEN' forces PostgreSQL to perform a Sequential Scan — reading all 5 million rows on disk (O(N))!

Adding a B-Tree Index creates a balanced sorted tree pointer structure on disk, reducing lookups from O(N) to O(log N) (~3–4 disk hops for millions of rows!).

Index Trade-off (Interview Gold!) Indexes make READs (SELECT) dramatically faster, but make WRITEs (INSERT, UPDATE, DELETE) slightly slower and consume extra disk/RAM, because Postgres must update every index tree whenever a row changes! Never index blindly — index columns used in WHERE, JOIN, and ORDER BY.

Part C: ACID Transactions & Connection Pooling

  • A — Atomicity: All-or-nothing (when reassigning a ticket AND writing an AuditLog entry inside prisma.$transaction(...), if AuditLog fails, the ticket assignment rolls back!).
  • C — Consistency: Constraints (Foreign keys, NOT NULL, UNIQUE) are never violated.
  • I — Isolation: Concurrent transactions don't corrupt each other (preventing double-claiming the same ticket).
  • D — Durability: Once committed, data survives power crashes (Write-Ahead Log / WAL).
  • Connection Pooling: Opening a fresh TCP + auth connection to PostgreSQL per HTTP request is expensive (~20–50ms) and Postgres only handles ~100–300 direct connections cleanly. Prisma / PgBouncer maintains a pool of reusable open connections shared across Express requests.

Day 3 System Design Interview Questions

Q1: Your Support Operations Center query SELECT * FROM tickets WHERE org_id = 5 AND status = 'OPEN' ORDER BY created_at DESC is slow on 2M rows. What index do you add and why does column order matter?
Show Answer

Add a Composite Index: CREATE INDEX idx_tickets_org_status_created ON tickets(org_id, status, created_at DESC);. Column order matters (Leftmost Prefix Rule): equality filters (org_id, status) go first to narrow down the slice, and the range/sort column (created_at) goes last so Postgres reads results already in sorted order!

DSA #7: Valid Sudoku (LeetCode #36 — Medium)

Problem: Determine if a 9 x 9 Sudoku board is valid (no duplicates in any row, column, or 3 x 3 sub-box). Empty cells are '.'.

  • Key Trick: Map every cell (r, c) to its 3 x 3 box index using integer division: box = Math.floor(r / 3) * 3 + Math.floor(c / 3) (values 0 through 8)!
  • Maintain 9 row Sets, 9 col Sets, and 9 box Sets. Time: O(81) = O(1) constant!
function isValidSudoku(board) {
  const rows = Array.from({ length: 9 }, () => new Set());
  const cols = Array.from({ length: 9 }, () => new Set());
  const boxes = Array.from({ length: 9 }, () => new Set());

  for (let r = 0; r < 9; r++) {
    for (let c = 0; c < 9; c++) {
      const val = board[r][c];
      if (val === ".") continue;

      const boxIdx = Math.floor(r / 3) * 3 + Math.floor(c / 3);
      if (rows[r].has(val) || cols[c].has(val) || boxes[boxIdx].has(val)) {
        return false;
      }
      rows[r].add(val);
      cols[c].add(val);
      boxes[boxIdx].add(val);
    }
  }
  return true;
}

DSA #8: Encode and Decode Strings (LeetCode #271 — Medium)

Problem: Design an algorithm to encode a list of strings to a single string, and decode that single string back to the exact original list. Strings can contain ANY character (including commas, hashes #, spaces, or empty strings!).

  • Why simple delimiter fails: Joining with "," or "#" breaks if a string itself contains "a#b"!
  • Optimal (Length-Prefix Framing): Prefix every string with length + "#"! E.g. ["lint", "co#de", ""] → "4#lint5#co#de0#". During decode, read digits until # to learn exact length len, then slice exactly len characters — regardless of what characters are inside!
function encode(strs) {
  return strs.map(s => `${s.length}#${s}`).join("");
}

function decode(str) {
  const res = [];
  let i = 0;
  while (i < str.length) {
    let j = i;
    while (str[j] !== "#") j++; // Find delimiter after length digits
    const len = Number(str.slice(i, j));
    const wordStart = j + 1;
    res.push(str.slice(wordStart, wordStart + len));
    i = wordStart + len;
  }
  return res;
}
// Time: O(N) total characters, Space: O(1) extra (excluding output)

DSA #9: Longest Consecutive Sequence (LeetCode #128 — Medium)

Problem: Given an unsorted array of integers nums, return the length of the longest consecutive elements sequence. Must run in O(n) time! (So sorting in O(n log n) is not allowed).

  • Core Intuition: Put all numbers in a Set (O(n)). How do we avoid re-scanning sequences? ONLY start counting forward when num is the START of a sequence — meaning !set.has(num - 1)!
  • Because we only walk forward from sequence heads, every number in the Set is visited at most twice → guaranteed O(n)!
function longestConsecutive(nums) {
  const numSet = new Set(nums);
  let longest = 0;

  for (const num of numSet) {
    // Only begin counting if 'num' has no left neighbor (it's a sequence start!)
    if (!numSet.has(num - 1)) {
      let current = num;
      let streak = 1;

      while (numSet.has(current + 1)) {
        current++;
        streak++;
      }
      longest = Math.max(longest, streak);
    }
  }
  return longest;
}
// Dry run: [100, 4, 200, 1, 3, 2]
// 100 -> no 99 -> streak 1.
// 4   -> has 3 -> SKIP!
// 200 -> no 199 -> streak 1.
// 1   -> no 0 -> counts 1,2,3,4 -> streak 4! (max=4)
// 3,2 -> have left neighbors -> SKIP! -> returns 4.
// Time: O(n), Space: O(n)
